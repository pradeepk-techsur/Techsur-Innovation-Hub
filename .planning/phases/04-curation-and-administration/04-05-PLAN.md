```typescript
async function getRecord(id: string) {
  try {
    const cookieHeader = (await cookies()).toString();
    const res = await fetch(
      `${process.env.NEXT_PUBLIC_APP_URL ?? 'http://localhost:3000'}/api/v1/curator/records/${id}`,
      { cache: 'no-store', headers: { Cookie: cookieHeader } }
    );
    if (res.status === 404) return null;
    if (!res.ok) throw new Error(`Failed to fetch record: ${res.status}`);
    return (await res.json()).data;
  } catch {
    return null;
  }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server→server (loopback) | SSR page calling its own API route via HTTP; cookie forwarded from the incoming request context |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05-01 | Information Disclosure | `cookies().toString()` forwarded in loopback Cookie header | mitigate | The forwarded value is the exact same cookie the user sent — no additional secrets are introduced. The loopback target (`/api/v1/curator/*`) enforces its own `requireRole()` check and will return 403 if the session is invalid. Cookie is `httpOnly` (set in `session.ts:setSessionCookie`) so it is never readable by client JS. |
| T-04-05-02 | Tampering | Cookie string passed to fetch headers | accept | Cookie value originates from `next/headers` (the verified incoming request context), not from user-controlled query params or request body. No interpolation of untrusted data into the header. Residual risk: if `NEXT_PUBLIC_APP_URL` is misconfigured, the loopback target could differ — accepted as operational misconfiguration risk, not a code-level attack surface. |
</threat_model>
